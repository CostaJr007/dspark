# 📊 DSpark Benchmarks & Performance Methodology

## 1. Methodology

Every number in this file is **regenerable from code in this repository**. There
are two kinds of metrics:

1. **Structural counts** (API comparisons, pruning rates) are produced by
   integration tests that run the real engine through the real HTTP client
   path against a bundled local mock server (`dspark::client::spawn_mock_chat_server`).
   They are deterministic and asserted in CI.
2. **Wall-clock timings** use [Criterion.rs](https://github.com/bheisler/criterion.rs).
   The tournament benchmark executes the **full PPT algorithm end-to-end**
   (ring pass + pivot stages) per iteration — no precomputed arithmetic.

Run everything:

```bash
./scripts/bench_all.sh                                   # Criterion suites
cargo test -p dspark-core --test tournament_scaling_test # comparison counts
cargo test -p dspark-core --test pruning_reproducibility_test -- --nocapture
cargo run -p dspark-core --example cost_quality_harness  # tiered economics
```

## 2. PPT Tournament Scaling ($O(Nk)$ vs $O(N^2)$)

The implemented algorithm performs exactly:

```
comparisons(N, k) = N            (ring pass i -> i+1 mod N)
                  + (N-k)*k      (non-pivots vs pivots)
                  + C(k,2)       (pivots vs pivots)
```

with the runtime clamp `k = min(k_requested, max(N / 2, 1))`.
This count is **asserted over the wire** by
`tests/tournament_scaling_test.rs::tournament_comparisons_match_formula`.

| Candidates ($N$) | Effective $k$ | Tournament Comparisons | All-Pairs ($O(N^2)$) | Reduction |
|---|---|---|---|---|
| $N=3$ | 1 (clamped) | 5 | 3 | **−67% (do not use PPT here)** |
| $N=5$ | 2 (clamped) | 12 | 10 | **−20% (still overhead)** |
| $N=10$ | 3 | 34 | 45 | **24.4%** |
| $N=20$ | 3 | 74 | 190 | **61.1%** |
| $N=50$ | 3 | 194 | 1,225 | **84.2%** |
| $N=100$ | 3 | 394 | 4,950 | **92.0%** |

> ⚠️ **Honesty note:** PPT is an *overhead* below N≈10 because the ring pass is
> paid up-front. It only pays off once `(N-k)·k` dominates, i.e. **N ≥ 10**.

### End-to-end latency (Criterion)

`cargo bench -p dspark-core --bench pivot_tournament` measures
`pivot_tournament_e2e/full_tournament/N={3,5,10,20}`: each iteration spawns the
full async orchestration and issues exactly `comparisons(N, 3)` HTTP requests
to a localhost mock endpoint. Timings therefore include prompt construction,
concurrency control (semaphore), network round trips and ranking aggregation.

## 3. Local Confidence Pruning Efficiency

Generated by `tests/pruning_reproducibility_test.rs`, which cycles five block
archetypes of increasing complexity (pure getter → parser → state mutation →
deep branching → unsafe pointer writes) through the Confidence Head and the
default `CostScheduler` (budget: 20 remote calls):

| Trajectories ($N$) | Blocks / Trajectory | Total Blocks | Remote Verifications | Locally Pruned | Savings |
|---|---|---|---|---|---|
| 3 | 10 | 30 | 12 | 18 | **60.0%** |
| 5 | 50 | 250 | 20 | 230 | **92.0%** *(budget cap)* |
| 10 | 100 | 1,000 | 20 | 980 | **98.0%** *(budget cap)* |

> The budget cap is a **feature**: `CostScheduler::default()` enforces a hard
> ceiling on spend. Raise `max_api_calls` to trade money for verification
> coverage on large trajectories.

## 5. Tiered Economics (flagship escalation)

`examples/cost_quality_harness.rs` simulates the three deployment modes
(flagship-only / cheap-only / tiered with flagship refinement) over a
deterministic task stream using **declared, editable assumptions**. Sample
output with its default assumptions:

```
config            pass%  cheap calls     flagship        $ total
flagship-only      90.5            0          200         6.0000
cheap-only         58.0          200            0         0.3000
tiered             96.0         1800           26         3.4800
```

Interpretation under those assumptions: the tiered pipeline beats
flagship-only quality while spending ~58% of its cost, escalating only 13% of
tasks to the expensive model. **These pass rates are simulation outputs, not
measured model accuracy** — validate against your own workload before quoting.

## 6. Live Pilot (real APIs, sandbox-graded)

Unlike everything above, this is a **measured** run: the full tiered pipeline
against live provider endpoints, graded in an isolated Python sandbox.

| | |
|---|---|
| Date | 2026-08-22 |
| Tasks | 56 = 50 HumanEval + 6 open-ended creation |
| Cheap tier | `gpt-4o-mini` (drafting + tournament comparisons) |
| Flagship tier | `deepseek-v4-flash` (escalated refinement) |
| Total spend | **US$ 0.1082** ($0.0375 mini + $0.0707 v4-flash) |

### Results

| Configuration | pass@1 | Notes |
|---|---|---|
| B: cheap-only | 89.3% | single draft per task |
| A: flagship-only | 83.9% | reasoning budget must exceed thinking tokens (see notes) |
| C: best-of-3 random | 89.3% | expected value over the same drafts |
| V: verify-all (free) | 89.3% | first draft passing local tests wins |
| T: PPT pick, no escalation | 89.3% | tournament winner taken as final |
| **D: tiered complete** | **91.1%** | escalation policy refines hard cases |

**Q1 (tournament vs random):** +0.0 pts — in all 56 tasks the three drafts
were perfectly correlated (all pass or all fail); nothing to separate.
**Q2 (escalation):** +1.8 pts; the policy escalated exactly the 6 failing
tasks (precision 100%) and repaired 1.

### Reproduce

```bash
export OPENAI_API_KEY=...      # cheap tier
export DEEPSEEK_API_KEY=...    # flagship tier
python bench/run_real_bench.py # kill-switch at $0.45/provider
```

Per-task JSONL logs are written to `bench/results/results_<epoch>.jsonl`;
committed logs include both runs (`…5482` = first run with the anomaly below,
`…6401` = final clean run).

### Known pitfall: reasoning models need larger `max_tokens`

The first run (`results_1787455482.jsonl`) showed intermittent empty
completions from `deepseek-v4-flash`. Root cause: it is a *reasoning* model —
every response carries an internal `reasoning_content` block that consumes the
same `max_tokens` budget. With `max_tokens=600`, thinking sometimes exhausted
the cap and left `content` truncated/empty → spurious sandbox failures. The
runner now applies a higher per-provider ceiling. If you swap models, check
whether they emit reasoning blocks before setting small token caps.
